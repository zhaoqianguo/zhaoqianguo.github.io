循环依赖，两套模块系统两种活法

发表于2026-11-23|随笔
|阅读量:

我写前端的那几年，一直觉得 import 和 require 就是同一件事换了层语法。类型检查跑通，单测全绿，模块引用能有什么问题。

后来在一台服务器上被打脸。本地一切正常，某次只是挪了一行工具函数的引用位置，上线之后页面一加载就抛 ReferenceError: Cannot access 'X' before initialization。另一次更难受，同一个公共库被两个子依赖分别引了进来，运行时做 instanceof 判断返回了 false，全局鉴权上下文莫名其妙就丢了。

TypeScript 在这两件事上一句话都说不出来。在类型系统眼里每个导出都合法，可引擎底下跑的是两套完全不同的规矩。

这篇的骨架来自《深入解析 JavaScript 循环依赖与模块副作用》，原文发在 51Testing，作者没有署名，地址放在最后。它给的七段代码我都在 node v22.22.1 下重跑了一遍，下面出现的输出都是我这边打出来的。

这些词平时被叫成「导入提升」，听着像语法层面的代码置顶。它不是。它是两阶段生命周期在起作用，引擎先深度优先遍历整张图，再按拓扑顺序求值。

跨边界的双包灾难

单套系统内部的事还算好理解。真正难查的是两套混着用。

现在很多库为了兼顾老代码的 require 和新项目的 import，会在 package.json 里配条件导出，同一份源码编出两份产物：ESM 一份 .js，CJS 一份 .cjs。我在 /tmp 里伪造了这么一个包，两份产物里各写一个 Token 类，源码逐字相同：

代码一模一样，instanceof 一个 true 一个 false。因为在加载器眼里 ./dist/index.js 和 ./dist/index.cjs 是两个不同路径的文件，各自独立加载，各自生成互不相通的缓存。它们导出的 Token 是两个不同的构造函数，原型链都是分开的。

我顺手查了一下缓存，想看看是不是真的存了两份：

只看到一条。ESM 那份不在 require.cache 里，它有自己的一套模块表，两套缓存不共享。这个细节比原文说的「两份互不相通的缓存」更准确一点：不是同一张表里存了两行，而是两张表各存一行。

这个问题的破坏力取决于库里存了什么。要是留着数据库连接池、全局事件总线、用户 Session 单例，同一个进程里就真有两套状态在跑，一边改了登录凭证，另一边浑然不知。Webpack 或 Vite 全量打包时有时会被去重策略盖过去，走 Node 原生服务端就几乎百分之百撞上。

我现在怎么防

这些坑没法靠业务代码里到处打补丁解决，得在依赖形状和发包流程上挡。

第一件事是把共享逻辑下沉。A 和 B 互相引对方的常量、类型、小工具函数时，通常说明中间少了一层。把被公用的部分抽到 types.ts、constants.ts 这种叶子模块里，两边单向依赖它，环就断了。如果 A 真需要 B 的运行时实例，用参数或者依赖注入在运行时传进去，别在文件顶层把引用写死。

第二件事是管住模块顶层的副作用。顶层别直接发网络请求、读还没注入的环境变量、改全局对象。确实需要异步初始化的东西，显式导出一个 initClient() 或者一个 Promise，让业务层在明确的启动生命周期里 await 它，把控制权还回去，而不是赌加载顺序。

第三件事是发公共库之前用 npm pack 做真实安装烟测。源码目录里单测全绿不够。打个 .tgz，扔进干净的临时工程里装上，分别写一个 .mjs 和一个 .cjs 脚本跑最基础的引入，确认 import 和 require 拿到的 API 一致、类没分裂、单例没变两份。我上周给一个内部包补这一步的时候，第一次跑就查出 exports 字段漏配了 require 分支，CJS 侧一直在拿默认导出。

这七段代码前后跑了大概一小时，最有用的不是哪一条结论，是那个 require.cache 只有一条的输出。它让我意识到所谓「两套系统」不是抽象的比喻，它们在进程里真的各有一套自己的账本。
